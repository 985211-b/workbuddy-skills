大模型的上下文

Context / Context Window —— 模型的"工作内存"

① 是什么② 三个反直觉事实③ 怎么运作④ 实战案例⑤ 常见误区⑥ 记住这几点
上下文 = 模型一次推理能"看到"的全部信息；窗口 = 能装下的最大 token 数。
Karpathy 的类比：模型是 CPU，上下文窗口就是 RAM——参数里的知识再多，思考时只认窗口里的内容。

1窗口里都装了什么

2三个反直觉事实

🔄 输入输出共享

模型自己的回答也占窗口额度，不是"免费"的

🫥 塞进来 ≠ 记得住

无关信息越多，关键信息分到的注意力越少（context rot）

📉 标称 ≠ 有效

复杂任务下，模型常在标称值一半就开始失准

3怎么运作

💡 U 型注意力（Lost in the Middle）

注意力天然偏重开头和结尾。20 篇文档塞进上下文，中间位置的信息检索准确率可从 75% 掉到 55-60%。这是排 prompt 顺序的第一依据：核心放开头和结尾，背景放中间。

四个核心部件（点开看）
部件作用类比
自注意力每个 token 决定"关注谁"开会扫视全场
KV Cache算过的历史缓存不重算演算过程留着不擦
位置编码给每个 token 发座位号超长时座位号区分度下降
共享额度输入输出共用一块地写满必须擦旧的
为什么窗口不能无限大（点开看）

注意力的计算量是平方级：1 万 token 是 1 亿次关联，10 万 token 是 100 亿次。滑动窗口、稀疏注意力、FlashAttention 都是为压这堵墙而生。KV Cache 则是"用显存换速度"：80 层 64 头的模型每个 token 约占 1.3MB 缓存，百万 token 对话的缓存可超 1TB——这是超长输入定高价的底气，也是 Prompt Caching 存在的原因。

4实战案例

场景：电商客服文档问答，8000 篇文档（300 万 token）。
错误方案：40 万 token 全塞进 1M 窗口 → 成本 4 倍、首字延迟 8 秒、准确率反而更低（弱相关文档稀释注意力，关键条款被"中间遗忘"）。

正确做法：五步上下文预算管理
步骤做法
① 分预算系统提示 ≤2K，检索文档 ≤4K（top-3 片段），历史只留近 3 轮 + 更早摘要，输出预留 2K
② 检索代替塞入查询时只注入最相关的 3 个片段，延迟降到 1 秒级
③ 前缀缓存系统提示固定放最前，命中 Prompt Caching，成本降到零头
④ 位置编排核心约束放开头，当前问题放结尾，背景放中间
⑤ 留逃生舱仅"多文档对比"类问题走长上下文通道

效果：成本降约 85%，延迟 8s → 1.2s。结论：长上下文和 RAG 不是替代关系，是分工关系。

5常见误区

❌ 窗口越大越强

有效利用率才是真相。18 个前沿模型研究显示，复杂任务中间位置准确率普遍降 30%+。选型看真实数据表现，不看营销页。

❌ 长上下文将杀死 RAG

长上下文赢在"难以预先定位 + 需跨文档对照"；RAG 赢在"语料远超窗口 + 成本敏感"。企业级 TB 级语料，RAG 依然是唯一可行架构。

❌ 上下文 = 对话历史

系统提示、工具定义、检索结果、记忆文件全都是上下文。"上下文工程"（优化模型每次看到什么）已取代 prompt 工程，成为 Agent 时代核心学科。

6记住这几点

✅ 记忆锚点

  • 类比：上下文是 RAM 不是硬盘——断电（请求结束）即消失
  • 排布：重要信息放开头和结尾（U 型注意力）
  • 预算：像管钱一样管 token，检索代替塞入
  • 分工：RAG 收窄候选集，长上下文做联合推理

7五道测试题（点开看答案）

① 上下文窗口最本质的约束是？

✅ 长度有限，超出后早期内容会被截断或模型直接"看不见"

② "上下文工程"主要解决什么问题？

✅ 决定"送什么进模型、怎么排"，让有限窗口内的每一格都物尽其用。已取代 prompt 工程成为 Agent 时代核心学科

③ 上下文管理的"四病"不包括？

✅ 训练数据污染（其余都是：信息丢失 / 注意力稀释 / 窗口溢出 / 成本失控）

④ 关于 RAG，正确的是？

✅ 把外部知识检索后注入上下文，弥补模型的知识截止与私域知识缺口，不靠"训练得更全"

⑤ 长对话中防"忘约定"最直接的方法是？

✅ 定期摘要压缩 + 关键事实写入外部记忆文件，下次会话再读回
